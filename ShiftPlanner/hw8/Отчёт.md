# Отчёт: HW8. Стратегии обновления приложения

## Приложение и подготовка к релизам

В качестве приложения используется ShiftPlanner: FastAPI backend, React frontend и PostgreSQL. Бизнес-состояние хранится во внешней для pod'ов PostgreSQL, поэтому реплики backend взаимозаменяемы. В версии приложения добавлены endpoint `GET /version` и заголовки `X-App-Version` / `X-App-Release`. Версию можно задавать при сборке образа. В Kubernetes для каждой версии предусмотрены readiness-проба `/health/db` и liveness-проба `/health`.

Для учебного прогона собраны два образа из одного исходного кода с release-идентификаторами `v1` и `v2`. Такая метка позволяет проверить маршрутизацию и откат, не вводя несовместимое изменение API или схемы PostgreSQL в демонстрационном стенде.

Envoy Gateway установлен в minikube, а правила маршрутизации заданы ресурсами Gateway API `Gateway` и `HTTPRoute`. Для каждой версии созданы отдельные Service и Deployment с двумя репликами. База данных общая, так что миграции схемы должны быть совместимы со старой и новой версиями на протяжении переключения.

## Стратегии

| Стратегия | Настройка | Что демонстрируется | Откат |
|---|---|---|---|
| Rolling | `RollingUpdate`, `maxUnavailable: 0`, `maxSurge: 1`; обновление образа backend 1.0.0 → 2.0.0 | Новые pod'ы становятся Ready по одному, старые выводятся после готовности новых. Endpoint `/version`, rollout status и pod logs подтверждают переход | `kubectl rollout undo deployment/backend -n shiftplanner` |
| Blue/Green | Два набора pod'ов; HTTPRoute направляет 100% запросов на v1 или v2 | Мгновенное переключение маршрута blue → green и возврат green → blue | Повторно применить `routes/blue-v1.yaml` |
| Canary | HTTPRoute weights 90/10 → 50/50 → 0/100 | Доля ответов v1/v2 меняется ступенчато; скрипт считает версии ответов в выборке | Применить `routes/blue-v1.yaml` |
| A/B | Заголовок `X-Experiment: beta` направляет на v2; остальные запросы — на v1 | Одинаковый endpoint возвращает разные `X-App-Version` в зависимости от аудитории | Применить `routes/blue-v1.yaml` |
| Shadow | Ответы клиенту даёт v1; Gateway отправляет копию запроса на v2 и игнорирует её ответ | Запрос виден в логах v2, клиентский заголовок версии остаётся v1 | Применить `routes/blue-v1.yaml` |

## Примечание по результатам

Кластер minikube, Envoy Gateway, оба release Deployment и маршруты Gateway API развёрнуты и проверены. Оба release pod-набора имеют по 2 Ready реплики; у приложения доступны readiness `/health/db`, liveness `/health`, а версия видна в JSON и response headers. Gateway доступен локально через port-forward; у его LoadBalancer Service в minikube нет внешнего IP, что ожидаемо без tunnel/load-balancer.

Видео всех пяти стратегий записаны и приложены в папке `videos/`.
