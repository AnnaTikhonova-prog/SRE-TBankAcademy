# SLI, SLO и SLA для ShiftPlanner

## Сервис и стек наблюдаемости

ShiftPlanner — учебное приложение для планирования рабочих смен на FastAPI и PostgreSQL. VictoriaMetrics Single собирает метрики каждые 15 секунд по Kubernetes pod discovery. Backend публикует OpenMetrics на `/metrics`; middleware считает HTTP-запросы и их длительность. `postgres-exporter` в sidecar-контейнере публикует `pg_up`.

В качестве трёх SLI используются метрики предыдущего задания:

1. `shiftplanner_http_requests_total{method,path,status}` — счётчик HTTP-запросов. Доступность API вычисляется как доля ответов 2xx среди всех запросов. `/health`, `/health/db` и `/metrics` из SLI пользовательского трафика исключаются.
2. `shiftplanner_http_request_duration_seconds_bucket{method,path,le}` — histogram длительности запроса. Latency SLI — доля запросов длительностью не более 500 мс.
3. `pg_up` — gauge PostgreSQL exporter: `1`, если exporter может подключиться к PostgreSQL, иначе `0`. DB SLI — доля scrape samples со значением `1`.

`readinessProbe` на `/health/db` не направляет запрос в Service, пока база недоступна; `livenessProbe` на `/health` перезапускает зависший процесс. Это Kubernetes probes, а не сами SLI: численные SLI рассчитываются в VictoriaMetrics из собранных метрик.

## Формулировки SLI и SLO

Окно оценки SLO — скользящие 30 дней. Для оперативной демонстрации в vmui используется такое же выражение за 5 минут (`[5m]`), где короткое окно помогает увидеть эффект тестовой нагрузки. `rate()` по счётчикам корректно учитывает reset при перезапуске pod.

### SLI 1 — доступность запросов API

Формула:

`availability = успешные пользовательские запросы 2xx / все пользовательские запросы × 100%`.

PromQL (значение от 0 до 1; в vmui выберите Graph):

```promql
sum(rate(shiftplanner_http_requests_total{namespace="shiftplanner",status=~"2..",path!~"/health|/health/db|/metrics"}[5m]))
/
clamp_min(sum(rate(shiftplanner_http_requests_total{namespace="shiftplanner",path!~"/health|/health/db|/metrics"}[5m])), 1e-9)
```

За 30 дней замените `[5m]` на `[30d]`, чтобы получить оценку окна SLO. Целевой SLO: **не менее 99.5% успешных запросов**.

### SLI 2 — latency API

Формула:

`latency SLI = запросы с длительностью ≤ 0.5 секунды / все пользовательские запросы × 100%`.

PromQL:

```promql
sum(rate(shiftplanner_http_request_duration_seconds_bucket{namespace="shiftplanner",le="0.5",path!~"/health|/health/db|/metrics"}[5m]))
/
clamp_min(sum(rate(shiftplanner_http_request_duration_seconds_count{namespace="shiftplanner",path!~"/health|/health/db|/metrics"}[5m])), 1e-9)
```

Целевой SLO: **не менее 95% пользовательских запросов быстрее или равны 500 мс**. Histogram bucket `le="0.5"` является кумулятивным и напрямую считает подходящие запросы.

### SLI 3 — доступность PostgreSQL

Формула:

`DB availability = scrape samples с pg_up=1 / все scrape samples × 100%`.

PromQL:

```promql
100 * avg_over_time(pg_up{namespace="shiftplanner"}[5m])
```

Целевой SLO: **не менее 99.9% scrape samples за 30 дней имеют `pg_up=1`**. Это индикатор доступности базы с точки зрения exporter, а не транзакционной успешности каждой операции.

## SLA приложения

Учебное внешнее обязательство ShiftPlanner: месячная доступность пользовательского API не ниже **99.0%** по request-based SLI из первого раздела, рассчитанная за календарный месяц. Доступность ниже 99.0% означает нарушение SLA. Ошибки клиентской валидации 4xx включены в знаменатель и считаются плохими запросами; health/readiness и scrape endpoint исключены. Такое правило консервативно и делает результат воспроизводимым.

Формула SLA:

`SLA availability = successful user requests / all user requests × 100%`.

Допустимое время недоступности при 99.0% за 30-дневный месяц: `30 × 24 × 60 × (1 − 0.99) = 432 минуты` (7 ч 12 мин). SLA опирается на тот же сигнал, что SLI доступности, но имеет отдельный порог 99.0%; SLO доступности 99.5% строже.

## Графики SLI, SLO и SLA в vmui

Откройте `http://localhost:8428/vmui/` после port-forward к Service VictoriaMetrics. Для каждого выражения выберите режим Graph и нажмите Execute. Чтобы сравнить линии с порогом, используйте `or vector(0.995)` для availability, `or vector(0.95)` для latency, `or vector(0.999)` для PostgreSQL; SLA-порог — `or vector(0.99)`. Удобнее вывести пороги отдельными запросами в том же графике:

```promql
vector(0.995)
vector(0.95)
vector(0.999)
vector(0.99)
```

## Описание изменений приложения для скринкаста

Для оценки SLI в FastAPI добавлен HTTP middleware, который регистрирует количество запросов по шаблону маршрута, HTTP-методу и коду ответа, а также наблюдает длительность каждого запроса в histogram. Метрики доступны в формате OpenMetrics на endpoint `/metrics`; сам endpoint метрик не учитывается в пользовательском трафике. Имена маршрутов берутся из шаблонов FastAPI, поэтому в метки не попадают конкретные идентификаторы пользователей и другие значения с высокой кардинальностью.

В Kubernetes настроен сбор этих метрик VictoriaMetrics с backend pod’ов. Доступность PostgreSQL независимо наблюдается через `postgres-exporter`, работающий sidecar-контейнером и публикующий `pg_up`. Для проверки состояния приложения используются Kubernetes `livenessProbe` на `/health` и `readinessProbe` на `/health/db`.

На демонстрации сначала формируется успешный фон запросами к `/openapi.json` (HTTP 200), затем отправляются запросы к несуществующему маршруту (HTTP 404). Middleware учитывает оба результата: успешные ответы входят в числитель и знаменатель availability SLI, а ответы 404 — только в знаменатель. Поэтому после сбора новых samples линия доступности на графике снижается и может опуститься ниже SLO 99.5% и SLA 99%. Запросы 404 не изменяют данные PostgreSQL, поэтому DB SLI остаётся стабильным. После прекращения ошибок последующие успешные запросы улучшают краткосрочный SLI по мере обновления пятиминутного окна.

В демонстрационных графиках используется окно `[5m]`, чтобы изменение было видно во время записи. Целевые SLO оцениваются на скользящем 30-дневном интервале, а SLA доступности — за календарный месяц. Пятиминутный график показывает поведение индикатора, но сам по себе не подтверждает месячное соблюдение SLO или SLA.
