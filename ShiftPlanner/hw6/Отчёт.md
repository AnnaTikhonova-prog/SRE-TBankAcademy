# Алерты ShiftPlanner

## Схема

VictoriaMetrics Single собирает метрики FastAPI и Python runtime с `/metrics`, а также `pg_up` от `postgres-exporter`. vmalert выполняет правила раз в 15 секунд, отправляет состояния в Alertmanager. Alertmanager направляет email-уведомления в MailHog — локальный SMTP-приёмник для демонстрации; реальные внешние адреса и SMTP credentials не используются.

## Выбранные алерты

| Alert | Условие | Назначение |
| --- | --- | --- |
| `ShiftPlannerHighRequestErrorRate` | Доля ответов 4xx/5xx выше 10% за 5 минут, непрерывно 1 минуту | Замечает рост неуспешных пользовательских запросов; health и metrics исключены |
| `ShiftPlannerHighP95Latency` | p95 длительности запросов выше 500 мс 2 минуты | Сигнал деградации времени ответа API |
| `PythonProcessMemoryHigh` | RSS процесса Python выше 300 MiB 5 минут | Рантайм-алерт на возможную утечку/рост потребления памяти |
| `PythonBackendTargetDown` | scrape target backend имеет `up=0` или ряд `up` отсутствует 1 минуту | Показывает, что Python backend недоступен для сбора метрик |

## Обоснование порогов

- **Ошибки API — более 10% в скользящем окне 5 минут, `for: 1m`.** В HW5 месячный SLA доступности задан как 99%, а SLO — 99.5%; 10% ошибок значительно превышают оба допустимых уровня и сигнализируют о быстром расходовании error budget. Порог не реагирует на единичный отказ: доля должна оставаться высокой не менее минуты.
- **p95 latency — более 500 мс в окне 5 минут, `for: 2m`.** Значение 500 мс совпадает с latency SLO HW5: не менее 95% пользовательских запросов должны укладываться в этот бюджет. Две минуты устойчивого превышения отсекают короткие пики.
- **Память Python — более 300 MiB, `for: 5m`.** У backend pod установлен memory limit 512 MiB. Порог 300 MiB оставляет около 212 MiB запаса до лимита для кратковременного роста и системных накладных расходов. Пять минут помогают выявить устойчивый рост RSS, а не краткий всплеск.
- **Backend target down — `up == 0` или ряд `up` отсутствует, `for: 1m`.** Сбор настроен раз в 15 секунд; минута соответствует примерно четырём неудачным циклам скрейпа. Проверка отсутствующего ряда нужна потому, что Kubernetes discovery удаляет pod-цель из списка скрейпа, когда backend Deployment масштабирован до нуля. Минута обнаруживает длительную недоступность, но не оповещает из-за единичного пропуска.

Окна `[5m]` сглаживают краткосрочный шум; `for` требует, чтобы условие оставалось истинным заданное время. Значения являются учебными порогами для данного стенда, а не результатом анализа исторической статистики production-нагрузки.

## Доставка уведомлений

Alertmanager группирует уведомления по `alertname` и `namespace`, отправляет их в локальный MailHog по SMTP. Web UI MailHog доступен на `http://localhost:8025` через port-forward; принятые письма являются скриншотируемыми уведомлениями. В конфигурации используются демонстрационные адреса `.test`.

## Проверка срабатывания

Для проверки `ShiftPlannerHighRequestErrorRate` в backend отправлено 150 запросов к несуществующему маршруту; они получили 404 и не изменили данные базы. После превышения порога более 10% в течение одной минуты vmalert перевёл правило из `pending` в `firing`. Alertmanager доставил уведомление на демонстрационный адрес `sre-student@shiftplanner.test`; письмо появилось в MailHog. Настроены ссылки на UI vmalert `http://localhost:8880/vmalert/`, Alertmanager `http://localhost:9093` и MailHog `http://localhost:8025`.

Для проверки `PythonBackendTargetDown` Deployment `backend` временно масштабирован с трёх реплик до нуля. Поскольку Kubernetes discovery удаляет исчезнувшие pod-цели, правило проверяет как `up == 0`, так и отсутствие ряда `up`. Через одну минуту vmalert перевёл алерт в `firing`, Alertmanager отправил письмо в MailHog. После проверки backend восстановлен до трёх реплик.
