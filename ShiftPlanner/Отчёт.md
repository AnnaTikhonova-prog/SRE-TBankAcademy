# Отчёт по домашнему заданию: клиент-серверное приложение

## Проект

**ShiftPlanner (учебная версия)** — адаптация командного летнего проекта
[shift-happens-daily/ShiftPlanner](https://github.com/shift-happens-daily/ShiftPlanner)
под требования задания.

Из исходного проекта намеренно убраны избыточно сложные для учебного
приложения части:

- автоматическая генерация расписания солвером OR-Tools (тяжёлая
  зависимость, ~800 строк логики) — заменена ручным назначением смен
  менеджером через обычный CRUD;
- email-подтверждение регистрации и сброс пароля через SMTP;
- импорт требований из Excel (.xlsx);
- мобильные клиенты (Android/iOS);
- боевой nginx с certbot/SSL — заменён компактным nginx внутри
  контейнера фронтенда;
- связи «многие-ко-многим» сотрудник↔филиал/должность — упрощены до
  прямых внешних ключей.

Оставлены и приведены к методологии 12 факторов: JWT-аутентификация,
ролевая модель (менеджер/сотрудник), PostgreSQL как единственное
хранилище состояния, HTTP/REST API, контейнеризация.

## Доменная область

Планирование рабочих смен в небольших компаниях сферы услуг (кафе,
магазины, сервисные точки). Менеджер создаёт компанию, заводит филиалы и
должности, приглашает сотрудников кодом приглашения и назначает им
смены. Сотрудник указывает свою недельную доступность и просматривает
назначенные смены.

## Стек реализации

| Слой | Технологии |
|---|---|
| Фронтенд | React 18, Vite, axios; раздаётся nginx |
| Бэкенд | Python 3.12, FastAPI, SQLAlchemy 2, python-jose (JWT), bcrypt |
| БД | PostgreSQL 16 |
| Инфраструктура | Docker, docker-compose |

Взаимодействие фронтенда с бэкендом — HTTP/REST (HTTP/1.1), JSON.
Стек легковесный: бэкенд — один процесс uvicorn, фронтенд — статика
под nginx, БД — стандартный образ postgres:16-alpine.

## Основные сущности

| Сущность | Таблица | Описание |
|---|---|---|
| Пользователь | `users` | Учётная запись: имя, email, bcrypt-хеш пароля, роль (`manager`/`employee`) |
| Компания | `companies` | Название, адрес, уникальный код приглашения, владелец-менеджер |
| Филиал | `branches` | Точка компании: название, адрес |
| Должность | `positions` | Должность внутри компании (бариста, кассир, …) |
| Сотрудник | `employees` | Профиль: связка пользователь↔компания + филиал, должность, признак активности |
| Доступность | `employee_availability` | Недельные интервалы, когда сотрудник может работать |
| Смена | `shifts` | Дата, время начала/конца, филиал, должность, назначенный сотрудник |

CRUD-операции реализованы для всех сущностей (см. таблицу API в README.md).

## Соответствие методологии 12 факторов

### I. Кодовая база (Codebase)

Весь проект — одна кодовая база в одном репозитории git
(`backend/`, `frontend/`, `docker-compose.yml`). Из одной и той же
кодовой базы выполняются все развёртывания: локальное (dev) и боевое
(prod) — различаются только значениями переменных окружения.

### II. Зависимости (Dependencies)

- Бэкенд: `backend/requirements.txt` с точными версиями пакетов;
  установка выполняется в изолированный Docker-образ
  (`pip install -r requirements.txt`), приложение не опирается на
  системные пакеты хоста.
- Фронтенд: `frontend/package.json` + зафиксированный
  `package-lock.json`; сборка воспроизводимо выполняется через
  `npm ci` внутри Docker-образа.
- Базовые образы зафиксированы: `python:3.12-slim`, `node:20-alpine`,
  `nginx:1.27-alpine`, `postgres:16-alpine`.

### III. Конфигурация (Config)

Вся конфигурация — в переменных окружения, в коде секретов нет:

- `DATABASE_URL`, `JWT_SECRET_KEY`, `JWT_ALGORITHM`,
  `ACCESS_TOKEN_EXPIRE_MINUTES`, `CORS_ORIGINS` — читаются бэкендом из
  окружения (`backend/app/config.py`, pydantic-settings);
- `JWT_SECRET_KEY` не имеет значения по умолчанию: если секрет не задан,
  приложение падает при старте (fail-fast), что исключает запуск
  с «зашитым» секретом;
- шаблоны `.env.example` (корневой и в `backend/`, `frontend/`)
  закоммичены, реальные `.env` исключены через `.gitignore`;
- параметры подключения к БД и порты пробрасываются в контейнеры через
  `docker-compose.yml` из корневого `.env`.

### IV. Подключаемые службы (Backing services)

PostgreSQL — подключаемый ресурс: бэкенд обращается к ней только по
`DATABASE_URL`. Замена локальной БД на управляемую (например, облачную)
требует изменения одной переменной окружения, без изменения кода.
Других подключаемых служб у учебной версии нет (SMTP из исходного
проекта удалён вместе с email-функциональностью).

### V. Сборка, выпуск, выполнение (Build, release, run)

Стадии строго разделены:

- **Build:** `docker compose build` — сборка образов
  (backend: pip-зависимости + код; frontend: `npm ci` + `vite build`
  в многоступенчатом Dockerfile);
- **Release:** образ + конфигурация окружения (`.env`) = релиз;
- **Run:** `docker compose up` — запуск контейнеров из собранных образов.

Изменение конфигурации не требует пересборки кода (кроме
`VITE_API_URL`, который по природе SPA вшивается в статику на этапе
сборки — это отражено в комментарии в `frontend/Dockerfile`).

### VI. Процессы (Processes)

Приложение stateless:

- аутентификация — stateless JWT: сервер не хранит сессии и списки
  выданных токенов (в исходном проекте был in-memory реестр активных
  токенов — это нарушало фактор VI и мешало масштабированию, в учебной
  версии он удалён; выход из аккаунта выполняется на клиенте);
- всё изменяемое состояние — только в PostgreSQL;
- следствие: любой запрос может обработать любой экземпляр бэкенда.

### VII. Привязка портов (Port binding)

Сервисы самодостаточны и сами биндят порты: бэкенд слушает `0.0.0.0:8000`
(uvicorn), фронтенд-nginx — `0.0.0.0:80`. Внешний веб-сервер не нужен.
Наружу порты публикуются через `docker-compose.yml`
(`BACKEND_PORT`, `FRONTEND_PORT` — настраиваются через env).

### VIII. Параллелизм (Concurrency)

Благодаря stateless-бэкенду приложение масштабируется горизонтально:
можно поднять несколько реплик (`docker compose up --scale backend=N`
перед балансировщиком или `uvicorn --workers N`), все они работают с
общей БД. Это задел для домашнего задания по балансировке трафика.

### IX. Утилизация (Disposability)

- Быстрый запуск: slim/alpine-образы, нет тяжёлой инициализации;
- graceful shutdown: uvicorn корректно обрабатывает SIGTERM
  (завершает обработку текущих запросов), postgres — штатно
  останавливается по сигналу от Docker;
- настроены healthcheck'и (`pg_isready`, `/health`), поэтому оркестратор
  знает, когда сервис реально готов принимать трафик.

### X. Паритет разработки и эксплуатации (Dev/prod parity)

Dev- и prod-окружения собираются из одних и тех же Dockerfile'ов и
запускаются одним и тем же `docker-compose.yml`; различия — только в
значениях переменных окружения. Разрыв минимален: и локально, и в
«проде» используется PostgreSQL 16 (а не SQLite локально), одинаковые
версии зависимостей, одинаковый способ запуска.

### XI. Логи (Logs)

Приложение пишет логи в stdout/stderr и ничего не знает про их
хранение: бэкенд — через стандартный `logging` и access-log uvicorn,
nginx — в stdout по умолчанию. Сбором занимается окружение
(`docker compose logs`, драйверы логирования Docker, в перспективе —
Loki/ELK).

### XII. Задачи администрирования (Admin processes)

Разовые админ-задачи выполняются отдельно от основных процессов, но в
том же окружении и с той же конфигурацией:

- инициализация схемы и демо-данных — скриптами
  `backend/db/schema.sql` и `seed.sql` при первом старте контейнера БД;
- ручные операции с БД: `docker compose exec db psql -U shiftplanner shiftplanner`;
- разовые команды бэкенда: `docker compose run --rm backend python -c "..."`.

**Честная оговорка:** полноценной системы миграций (Alembic) в учебной
версии нет — схема применяется только на пустом volume. Это осознанное
упрощение и пункт бэклога ниже.

## Что оставлено для дальнейших SRE-улучшений (бэклог)

Сознательно не реализовано в учебной версии — это темы следующих
домашних заданий:

1. **Наблюдаемость:** нет метрик (Prometheus `/metrics`), нет
   централизованного сбора и структурирования логов (JSON), нет трейсинга.
2. **Балансировка и отказоустойчивость:** по одной реплике каждого
   сервиса; нет внешнего балансировщика перед репликами бэкенда.
3. **Безопасность периметра:** HTTP без TLS, нет rate limiting,
   секреты — в `.env` (не в Docker Secrets/Vault).
4. **Эксплуатация БД:** нет резервного копирования, нет миграций
   (Alembic), нет мониторинга соединений.
5. **CI/CD:** нет пайплайна сборки/тестов/деплоя (в исходном проекте
   был `.github/workflows/deploy.yml` — удалён вместе с боевым окружением).
6. **Тесты:** автотесты из исходного проекта зависели от удалённых
   фич (солвер, email); для учебной версии проверка выполняется
   smoke-сценарием через Swagger UI / curl (см. README).

## Как проверить работоспособность

```bash
cp .env.example .env
docker compose up --build
```

1. Открыть http://localhost:8080 — страница входа/регистрации.
2. Войти как `manager@example.com` / `manager123`: видны компания
   «Кофейня „Уютная“», код приглашения COFFEE42, филиалы, должности,
   сотрудники и смены на текущую неделю.
3. Создать/изменить/удалить филиал, должность, смену (CRUD).
4. Войти как `ivan@example.com` / `employee123`: видны свои смены,
   можно редактировать доступность.
5. API-документация: http://localhost:8000/docs (Swagger UI,
   авторизация кнопкой Authorize → логин демо-аккаунтом).
6. Health-эндпоинты: http://localhost:8000/health и
   http://localhost:8000/health/db возвращают `{"status": "ok"}`.
