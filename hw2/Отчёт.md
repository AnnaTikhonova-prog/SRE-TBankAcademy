# Отчёт по домашнему заданию «Запуск приложения в minikube»

## Приложение

Разворачивается приложение **ShiftPlanner** (учебная версия) из
предыдущего домашнего задания — клиент-серверное приложение для
планирования рабочих смен:

- **frontend** — React SPA, собранная статика раздаётся nginx, который
  также проксирует `/api/*` на бэкенд;
- **backend** — FastAPI (Python 3.12), REST API с JWT-аутентификацией,
  stateless (состояния в памяти нет, сессии не хранятся);
- **postgres** — PostgreSQL 16, хранит все данные приложения.

Исходный код приложения и Dockerfile'ы — в папках `backend/` и
`frontend/` этого архива. Манифесты — в папке `k8s/`.

## Подготовка образов

Образы собраны локально и загружены в minikube (без внешнего registry):

```powershell
minikube start --driver=docker
minikube docker-env --shell powershell | Invoke-Expression   # сборка сразу в docker-демоне minikube

docker build -t shiftplanner-backend:1.0 ./backend
docker build -t shiftplanner-frontend:1.0 ./frontend

minikube image load shiftplanner-backend:1.0
minikube image load shiftplanner-frontend:1.0
```

В манифестах для этих образов выставлено `imagePullPolicy: IfNotPresent`,
чтобы kubelet использовал локальный образ и не пытался скачать его из
внешнего registry.

## Использованные абстракции Kubernetes

| Абстракция | Где используется | Зачем |
|---|---|---|
| **Namespace** | `00-namespace.yaml` | Изоляция всех ресурсов приложения в `shiftplanner` |
| **Deployment** | postgres, backend, frontend | Декларативное управление подами и числом реплик; пересоздание при падениях |
| **Service (ClusterIP)** | `postgres`, `backend` | Стабильные DNS-имена и виртуальные IP для внутреннего взаимодействия; для backend — балансировка между репликами |
| **Service (NodePort)** | `frontend` (порт 30080) | Единственная точка входа в приложение с хост-машины |
| **PersistentVolumeClaim** | `postgres-pvc` (1 ГиБ) | Постоянное хранение данных PostgreSQL; minikube создаёт PersistentVolume автоматически (hostpath provisioner) |
| **ConfigMap** | `shiftplanner-config`, `postgres-initdb` | Несекретная конфигурация (env) и SQL-скрипты инициализации БД (схема + демо-данные) |
| **Secret** | `shiftplanner-secret` | Пароль БД и ключ подписи JWT (не светятся в ConfigMap) |
| **readinessProbe / livenessProbe** | все три Deployment | readiness: под не получает трафик, пока не готов (у backend проверяется и БД — `/health/db`); liveness: перезапуск зависшего контейнера |
| **resources (requests/limits)** | все три Deployment | Гарантия минимальных ресурсов и защита узла от перепотребления |

Осознанные решения:

- **postgres — Deployment, а не StatefulSet.** Для учебного стенда с одной
  репликой БД этого достаточно; `strategy: Recreate` корректно работает с
  PVC `ReadWriteOnce` (том нельзя смонтировать в два пода одновременно).
  В боевой эксплуатации для БД правильнее StatefulSet + headless Service.
- **Инициализация БД через ConfigMap + `/docker-entrypoint-initdb.d`.**
  Официальный образ postgres выполняет скрипты из этого каталога один раз
  при первом старте на пустом томе — тот же механизм, что в docker-compose
  из первого ДЗ. Схема и демо-данные появляются без ручных действий.
- **Backend stateless** (JWT без серверных сессий) — поэтому
  `kubectl scale` просто работает: новые реплики сразу взаимозаменяемы,
  а Service распределяет запросы между ними.

## Как сервисы взаимодействуют между собой

```text
браузер
   │  http://<minikube-ip>:30080
   ▼
Service frontend (NodePort) ──► Pod frontend (nginx)
                                   │  отдаёт статику React
                                   │  /api/* ──► proxy_pass http://backend:8000
                                   ▼
                              Service backend (ClusterIP:8000)
                                   │  балансировка по репликам
                                   ▼
                              Pod backend ×N (FastAPI)
                                   │  DATABASE_URL = postgresql+psycopg://...@postgres:5432/...
                                   ▼
                              Service postgres (ClusterIP:5432)
                                   ▼
                              Pod postgres ──► PVC postgres-pvc (данные на диске узла)
```

1. **Пользователь → frontend.** Браузер ходит на NodePort 30080; Service
   `frontend` передаёт трафик поду с nginx.
2. **frontend → backend.** nginx внутри пода frontend отдаёт статику, а
   запросы `/api/*` проксирует на `http://backend:8000` — имя `backend`
   разрешается через внутренний DNS кластера (kube-dns / CoreDNS) в
   ClusterIP одноимённого Service. Дальше Service равномерно
   распределяет запросы по готовым (ready) репликам backend.
3. **backend → postgres.** Бэкенд подключается к БД по адресу
   `postgres:5432` (тоже DNS-имя Service). Строка подключения собирается
   в переменной окружения `DATABASE_URL` из значений ConfigMap и Secret
   (подстановка `$(VAR)` в env манифеста).
4. **postgres → диск.** Данные БД лежат на PersistentVolume, выданном по
   PVC, поэтому переживают пересоздание пода.
5. **Конфигурация.** Все переменные окружения подов берутся из
   ConfigMap (несекретные) и Secret (пароль БД, JWT-ключ) — в образах
   секретов и конфигурации нет.

Готовность и порядок запуска: backend не становится Ready, пока его
`/health/db` не подтвердит доступность PostgreSQL, поэтому Service не
направляет трафик в «недогруженные» поды. Жёсткой зависимости запуска
нет — поды сами доходят до Ready по мере поднятия зависимостей
(readiness-пробы, а не оркестрация старта).

## Развёртывание и проверка

```powershell
kubectl apply -f ./k8s/
kubectl get pods -n shiftplanner -w        # ждём Running у всех подов
kubectl get all -n shiftplanner            # поды, сервисы, деплойменты
kubectl scale deployment backend -n shiftplanner --replicas=3
kubectl get pods -n shiftplanner           # 3 реплики backend
minikube service frontend -n shiftplanner  # открывает UI в браузере
```

Проверка в UI: вход менеджером `manager@example.com / manager123`
(компания, филиалы, должности, сотрудники, смены) и сотрудником
`ivan@example.com / employee123` (мои смены, доступность). Демо-данные
создаются скриптом `02_seed.sql` из ConfigMap `postgres-initdb`.

Процесс развёртывания, вывод подов, масштабирование и работа в UI
записаны на скринкасте (прилагается к архиву); пошаговый сценарий
демонстрации — в файле `DEMO.md`.
